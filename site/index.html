How it got there

How the driver works, what turned the project, and the tool that replays every lap.

How the driver works

The driver is one Python file of explicit rules. It contains no neural network and no trained model. The example driver supplied with the challenge aims for 300 km/h, never brakes and crashes on its first lap; everything below was built on top of it.

It works like a racing driver who has walked the track beforehand. The plan for the lap is worked out before the race. On the lap, the sensors decide every pedal and steering movement.

Track memory

Computed before the race, stored by distance from the start line

  • A racing line, computed from the track's geometry: where to be on the road every 10 m.
  • The speed that line allows at each point.
  • The road's rises and dips, read from the track file.
  • A few stretches where the gear-change or steering settings differ.

Live sensors

Read every step, about 21 ms

  • Position, angle and slide against the line: the steering correction.
  • Actual speed against the stored speed: throttle or brake, and how hard.
  • Wheel speeds: anti-lock brakes and traction control.
  • Engine speed: gears and clutch.
  • 19 range beams: the braking plan wherever the stored speed is only a cap, and the steering at the start and finish.

Controls

Sent every step

  • Steering, throttle, brake, gear, clutch.
  • No pedal or steering value is ever replayed from memory.
  • Every step is written to a telemetry file, which is what the run viewer replays.

How a change earns its place

One mechanism per version, so its effect can be measured. In the final versions each candidate drove 730 laps with its settings and its plan deliberately nudged: 70 for the lap time, compared run by run against the version before, and 660 around the new values to look for a way off the road. Any damage, or any lap with the car's centre past the edge, rejected the version. Of 133 versions, 100 were kept, 11 were kept as groundwork for a later gain and 22 were rejected. The record of every one, with what was learned, is in the changelog.

The journey

For the first 105 versions the car drove on its sensors alone, because we held back track memory until the officials answered. That approach ran out at about 1:13.6: in batch 12 four of five versions were rejected, since a car cannot set up wide for a corner it does not yet know is coming. On 4 October the officials allowed a pre-mapped track, and the question that turned the project came three days later:

Since we can memorize the track can't we precompute the most optimal racing line and adjust that?

The last eight seconds came from that line, the speed it allows and the rulings that let the car use the whole road.

The last 29 versions, with the decision that opened each run of gains.

The run viewer

Every version's lap can be replayed in the browser: the car on a map of the track with its range beams, the pedals and steering step by step, and any two laps side by side to see where the time went. It is the tool that showed where the car had road it was not using.

For the judges

The technical summary, how IBM Bob was used, the deliverables and the full record.

Technical summary

The driver is a rule-based controller in one Python file. It contains no machine-learning model. Steering, braking, throttle and gear changes come from explicit logic reading the simulator's live sensors: 19 range beams, wheel speeds, engine speed, speed, track position and angle.

The project produced 133 tagged versions on the Corkscrew circuit (3,608 m) between 1 and 8 October 2026. The first completed lap was 2:43.38 (v0.2). The submitted version, v1.33, laps in 1:05.56, which is 97.82 seconds faster, with zero damage and the car's centre inside the track edge for the whole lap (largest |trackPos| 0.862).

Design. Track memory, computed offline from the track's geometry and stored by distance, holds a racing line, the speed it allows and the road's elevation. These are parameters, not replayed actions. Every step the live sensors correct the steering against the line, set the pedals from the car's actual speed against the stored speed, and run anti-lock braking, traction control and the gearbox.

Tooling. A harness runs up to four simulators at once and judges each candidate on hundreds of deliberately perturbed laps. An optimiser tunes single settings, and a pattern check catches steering wobble and on/off pedals. Every version is a Git tag with its telemetry.

Use of IBM Granite. IBM Bob did the analysis, the planning and the reviews described below. The driver's code was written with Claude Code.

Key challenge. On sensors alone the car cannot prepare for a corner it has not seen. The lap time stalled at 1:13.6 until the officials allowed a pre-mapped track.

Rules. Six questions of legality are recorded, each with a fallback version: four confirmed by the officials, two our own reading.

How IBM Bob and Granite were used

IBM Bob, the coding assistant built on IBM Granite, was this project's analyst, planner and reviewer. Its log holds 13 sessions between 1 and 6 October, and it drafted the outline of this page.

  • It opened the project. Bob found the driving function in the supplied driver, listed every sensor it reads and every action it sets, and wrote the first tuning card and the changelog format that all 133 versions use.
  • It gave a second opinion. After 72 versions Bob was asked for an analysis independent of the one in progress, and ran three specialists (a race engineer, a racing driver, a data analyst) over the code and the telemetry. Batch 7 put its plan to the test. The two suggestions that were measured, v0.73 and v0.74, were rejected, and that is recorded like every other result.
  • It planned how the work was run. Bob wrote the hand-off plan for the coding agent and the brief for running agents in parallel. Batch 9 tried it: gains that passed alone failed together, so the project went back to one agent per version.
  • It organised and reviewed. Bob restructured the repository, wrote its READMEs, reviewed the run viewer from four points of view (race engineer, driver, data analyst, first-time visitor) and built the viewer's first hosted phases.

Where each tool fitted best

Bob was at its best reading code, analysing data and planning. Its direct edits to the driver's control code were less dependable: in my experience about half of them left the lap slower or less stable. That is an impression from working with it, not a measured figure. So I settled early on a division of work. Bob handled analysis, planning and review, and the driver's code was written with Claude Code, with every version measured in the simulator before it was kept.

The driver itself contains no model. Granite helped build it; it does not drive it.

Rules, and what we would submit instead

Six times the driver began to rely on something whose legality was not obvious. Four were put to the officials and confirmed. Two are our own reading of those answers and were not asked separately. Each one names the version we would submit if it were turned down.

What the driver doesSinceStatusFallback

On track limits the officials' answer was: Use trackPos between −1 and +1 as the practical sensor-based check. This measures the car's position, rather than whether individual wheels cross the edge. On the judged lap the car's centre reaches 0.862 at its widest, 1037 m from the start line.
